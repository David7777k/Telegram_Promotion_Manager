# Telegram Promotion Studio 3.0

Проект архитектуры для Windows, 12 ноября 2026 года. [Состояние v2](PROJECT_STATUS.md) · [Этапы](IMPLEMENTATION_PLAN.md) · [Задачи](TASKS.md).

## 1. Границы и архитектурные решения

Локальный инструмент для согласованных размещений. Основной сценарий — продвижение канала с реальным контентом и понятными условиями подписки, по умолчанию 250 Stars каждые 30 дней. Интернет нужен только для операций Telegram. Черновики, редактор, анализ правил, ручная аналитика и демонстрация работают локально. Внешних AI API, сервера продукта и обязательных платных сервисов нет.

| Противоречие | Решение |
|---|---|
| Отправитель для согласованной площадки | Поддерживаются Bot API и штатный MTProto для личного аккаунта. Отправитель выбирается для каждой площадки явно, привязывается к согласованию и снимку задания. Права и идентичность перепроверяются непосредственно перед отправкой. Ограничение Telegram не меняет назначение. |
| Доступ к чату смешивается с согласием на рекламу | Три независимые проверки: идентичность чата, актуальные технические права выбранного бота, согласие с конкретными условиями. Публичность и отсутствие запрета согласия не создают. |
| Надёжный повтор конфликтует с неизвестным результатом | Bot API не даёт ключа идемпотентности для sendMessage/sendPhoto. После неопределённого результата публикация требует сверки. Локальная дедупликация защищает от двойной постановки, внешняя exactly-once недостижима. |
| Каталог и статистика подразумевают полный охват | Поддерживаются доступные диалоги, известные чаты и ограниченный интерактивный поиск. Отсутствующие метаданные, клики и деньги остаются неизвестными. |
| Запланированное время может наступить при закрытом приложении | Очередь сохраняется, исполнение только в открытом приложении и после явного включения на текущий сеанс. Просрочка более 1 часа требует перепланирования. |
| UX-бриф предлагает четыре раздела, ТЗ 3.0 — семь | Семь разделов полного приложения. Планировщик внутри «Кампаний», журнал открывается из статуса и Настроек. В промежуточной сборке показывать только готовые разделы. |
| ТЗ предлагает ранний редизайн, а исходники требуют сохранения данных | Макет и UI без реальных операций можно делать параллельно. Запись в рабочее хранилище и отправка включаются после проверок миграции и очереди. |
| Партнёрские публикации и Telegram Ads имеют разные правила | Раздельные профили проверки. Telegram Ads — вспомогательная редакционная проверка 160 символов без интеграции с рекламным кабинетом. |

UI вызывает use cases. Use cases используют домен и порты. Адаптеры реализуют порты и подключаются в bootstrap. Домен не импортирует Qt, SQLite или Telethon. Репозиторий не инициирует Telegram-запросов. Вводить порты по появлению реального шва. AccountDirectory.sync_dialogs/resolve/search/join_one возвращает DTO. BotPublisher.inspect/dispatch/create_paid_invite принимает конкретного бота и цель. Dispatch получает неизменяемый PublicationSnapshot и возвращает Receipt или типизированный исход. SecretStore.put/get/delete, Clock.now_utc и поддельные адаптеры делают сетевые и временные тесты воспроизводимыми.

Стек — CPython 3.12+ x64, PySide6 Widgets, стандартный sqlite3, zoneinfo + tzdata для Windows, стабильная ветка Telethon 1.x после проверки QR/2FA, httpx для async Bot API/multipart, тонкий Win32-адаптер DPAPI, pytest + pytest-qt, PyInstaller. Библиотеку QR добавить при реализации. Telethon уменьшает объём нативной сборки по сравнению с TDLib. Версии и транзитивные зависимости фиксируются после матрицы Python 3.12/3.13/3.14 и проверки Windows-сборки. Дополнительные ORM и планировщик не нужны для P0.

Qt GUI работает в главном потоке. Один выделенный поток держит asyncio loop и Telegram-клиенты. Отдельный последовательный DB worker владеет SQLite connection; короткие чтения в P0 тоже проходят через него. UI получает DTO и ошибки через queued signals, не блокируется на future.result. Тяжёлый импорт и подготовка фото — ограниченный фон. Системная блокировка одного процесса на профиль берётся до открытия базы. На закрытии прекратить выдачу новых сетевых вызовов, отменить чтения, ограниченно ждать начатых записей, сохранить результат либо неопределённость, закрыть Telegram и последним — DB worker. Принудительная остановка восстанавливается из журнала попыток.

## 4. SQLite и совместимость

Рабочий профиль в %LOCALAPPDATA%\TelegramPromotionStudio\: studio.sqlite3, assets, защищённые резервные копии. Демо — отдельный профиль с поддельными адаптерами. Миграции SQL с версией и checksum, foreign_keys=ON, busy_timeout=5000, synchronous=FULL, rollback journal DELETE в P0. WAL рассматривать после измерений и только на проверенной исправленной SQLite (3.51.3+ либо подходящий backport, включая 3.50.7 и 3.44.6). В окружении аудита SQLite 3.50.4. Короткие транзакции, BEGIN IMMEDIATE для резерва слотов, сеть вне транзакции. Время — UTC epoch seconds + IANA-зона ввода. UAH — integer minor units, цена Stars — integer; подтверждённые дробные величины сохраняются в точных единицах финансового источника.

Реализация P0 хранит управляемые фотографии в `publication_photos` как зашифрованные SQLite BLOB по SHA-256. Фото попадает в резервную копию вместе с заданием и не зависит от перемещения исходного файла. При переносе на другой Windows-профиль доступ к данным DPAPI требует отдельной проверки. Файловое хранилище остаётся вариантом для будущих больших вложений.

### Импорт v1/v2

1. Приоритет v2 %USERPROFILE%\.telegram_promotion_manager_v2\state.json. При отсутствии — v1 %USERPROFILE%\.telegram_promotion_manager\settings.json. Битый v2 запускает восстановление и отчёт. Исходники только read-only. Сохранить DPAPI-защищённый снимок исходных байтов, SHA-256 и проверить, что источник не изменился между чтением и фиксацией. Импорт рекомендует закрыть v2; одновременное изменение обнаруживается по отпечатку.
2. Валидировать верхний уровень и типы строк, фиксировать повреждения, конфликты ID, потерянные FK и диапазоны в отчёте и защищённом архиве. Для v2 сохранять ID кампаний/площадок/шаблонов/posts, журнал, last_sent, выбранную кампанию и известные настройки. V1: channel/link/price, targets, last_sent, templates; стабильный ID от вида источника и legacy key. Описание пустое, согласие требует проверки. Тот же SHA — идемпотентный no-op. Дополнительный импорт из другого снимка показывает конфликты и не перезаписывает молча.
3. V2 sent → историческая квитанция: сохранить время, текст, message ID, цену и показатели; если цена отсутствует, она неизвестна. Sending → needs_review. Planned → paused/legacy_reapproval. Failed/blocked → failed/blocked при доказанном отказе, иначе needs_review. Импортированные согласия требуют перепроверки. Старый ручной ноль без отметки ввода сохранять как исходное число, для аналитики трактовать как неопределённый. Секреты и live/auto не импортировать.
4. Наивное время v2 интерпретировать по выбранной IANA-зоне; предложить системную, DST gap/fold вывести на ручную проверку. V1 epoch переносить как абсолютное время. UAH читать через Decimal, спорное округление фиксировать. Импорт доменных строк, версию и итоговые счётчики фиксировать одной транзакцией; при сбое не трогать исходники и предыдущую БД.

## 5. Модули

### Telegram Accounts и Security

Bot Manager: маскированный токен → getMe → привязка ID → шифрование при выборе «Запомнить». MTProto: API ID/hash, QR или номер, штатный шаг кода/2FA. Машина disconnected → authenticating → needs_code / needs_2fa → connected, ветви expired/revoked/error. QR живёт по TTL в открытом диалоге, закрытие отменяет задачу, фоновый запрос не инициирует вход. get_me подтверждает идентичность. Telethon StringSession создаётся в памяти, после успешного входа хранится только как DPAPI ciphertext. Открытых .session/QR-файлов нет. В памяти код/пароль живут только на шаге входа.

«Отключить» закрывает соединение и паузит связанные задачи. «Удалить локальную сессию» удаляет активный секрет. Отдельный «Завершить сеанс Telegram» отзывает MTProto-сессию; если исход неизвестен, показать проверку через «Устройства». Токен бота отзывает пользователь через BotFather. После ротации проверить ID, права и hold.

DPAPI CurrentUser без machine scope. Защищаются токены, API hash, сессии, закрытые ссылки и снимки, содержащие такие ссылки. ACL каталога ограничен текущим пользователем. OTP, 2FA, QR, raw Telegram body и заголовки не пишутся на диск. Журнал строится из allowlist полей и нормализованных кодов. Убрать Telegram-токены, телефон, invite hash, полные URL и тексты из логов/диагностик. HTTP host фиксирован, TLS проверяется, redirects выключены. Пользовательские ссылки разбираются локально без HTTP-запросов по ним. CSV защищён от formula injection, закрытые ссылки и контакты исключены из экспорта по умолчанию.

DPAPI защищает данные на диске от другого профиля; процесс того же пользователя считается доверенным. Обычный backup — целостный снимок SQLite и manifest ресурсов без account_secrets. Закрытые ссылки сохраняются зашифрованными. При переносе на другой Windows-профиль они могут быть недоступны: показать состояние, сохранить историю, приостановить будущие задания до перепривязки. Restore всегда disarmed. Секреты удалять из копии БД с последующим построением чистого файла (например, VACUUM INTO), чтобы удалённые страницы не попали в архив.

### Group Discovery, согласия и правила

Источники: ручной ID/username/ссылка, TXT/CSV, диалоги аккаунта, интерактивный поиск, известные боту чаты. URI разбирать явно: t.me/telegram.me и поддержанные Telegram deep links; отличать username, приглашение, тему и ссылку на сообщение; отклонять userinfo и нестандартные порты. Username приводится к lower-case. Импорт — предпросмотр валидных строк, дубликатов и ошибок без сетевого запроса на каждую строку. После подтверждения пользователь может обновить метаданные выбранных площадок. Дедуп по каноническому числовому ID и aliases. При передаче username новому владельцу повторно проверить сопоставление, реальные публикации используют сохранённый числовой ID. Членство и права хранятся для конкретного аккаунта.

Фильтры: тип, категория, язык, диапазон участников, права, согласие, избранное/исключённое, ключевые слова. Nullable поля с указанием источника и времени. Парсер правил берёт описание, доступный pin и заметку оператора. Детерминированные словари и regex выделяют фрагменты о ссылках, медиа, частоте, времени, тематике. Запрет или конфликт блокирует до разбора оператором; отсутствие сигнала оставляет состояние «требуется подтверждение». Согласие записывается отдельно: кто, когда, условия, срок, площадка/тема, бот. Единичное вступление: pending_confirmation → ready → joined/already_member/request_pending/failed/needs_review; отмена допустима до запроса. Смена аккаунта требует нового подтверждения.

### Campaign Manager и платные ссылки

Кампания: draft → ready → active/paused → archived. Изменение предложения или шаблона создаёт ревизию. Draft → Preview → Approve формирует отдельный job на согласованную площадку и слот. Preview фиксирует текст, фото, кнопку, ссылку, цену, период, бота, Chat ID, тему и причину пропуска неготовой строки. Будущие правки не изменяют утверждённый payload. Изменения предложения, цены, ссылки или условий приостанавливают затронутые задачи до нового утверждения. Архивирование, отзыв согласия и отключение аккаунта не меняют историю. Структурированная проверка предложения связывает точную цену, период, ссылку и факт подтверждения контента с рендером.

Бюджет кампании — учётная величина. Предпросмотр показывает оценку суммы по площадкам и предупреждает о превышении; подтверждение оператором фиксируется. Исторические расходы вносятся отдельно. Отправка в Telegram не списывает согласованную стоимость размещения из внешнего кошелька.

Платные ссылки: основная, на кампанию либо на отдельную публикацию. Ссылка на один job даёт однозначное соответствие источника, если Telegram передал ссылку в событии. При изменении цены нужна новая версия предложения и подходящая ссылка. Запись create intent до вызова, ответ сохраняется атомарно. При таймауте оператор сверяет созданные приглашения в Telegram, только потом закрывает intent или привязывает найденную ссылку. Отзыв — отдельная операция владельца. Рендер и цена для аналитики берутся из утверждённого снимка.

### Spintax Engine

Синтаксис v3: переменная {{channel_link}}, выбор {Привет|{Здравствуйте|Добрый день}}, экранирование фигурных скобок, вертикальной черты и обратной косой черты обратной косой чертой. Лексер распознаёт двойную скобку раньше одиночной. AST Text, Variable, Sequence, Choice. В choice минимум две непустые альтернативы. Разрешённые переменные: channel_link, channel_name, price, subscription_period, campaign_name, description, topic, platform. Подстановка литеральная после выбора ветвей, без eval и повторной интерпретации. Ошибка содержит позицию, строку, столбец и ожидаемый токен.

Начальные бюджеты: 16 KiB UTF-8, глубина 16, 4096 узлов, 32 альтернативы на блок. Сумма для Choice, произведение для Sequence, насыщение на 1 000 001. Это число путей, уникальных строк может быть меньше. До 10 вариантов за 100 попыток с дедупом итогового текста, воспроизводимый RNG в тестах. Сохранить версию движка, подпись варианта и утверждённый текст; очередь не генерирует заново. V2 шаблоны получают syntax_version=2. Конвертер заменяет известные одиночные переменные, экранирует остальное, показывает diff и сохраняет исходник. Подсветка, сравнение, история и восстановление ревизий; визуальный конструктор добавляется после стабилизации грамматики.

### Scheduler и Send Executor

~~~mermaid
stateDiagram-v2
    [*] --> Draft
    Draft --> Queued: утверждение снимка
    Queued --> Paused: пауза или просрочка
    Paused --> Queued: перепроверка
    Queued --> Claimed: захват слота
    Claimed --> Dispatching: записан intent
    Claimed --> Blocked: проверка не прошла
    Claimed --> Queued: восстановление до intent
    Dispatching --> Sent: квитанция
    Dispatching --> Blocked: подтверждённый 429
    Dispatching --> Failed: однозначный отказ
    Dispatching --> NeedsReview: исход неизвестен
    NeedsReview --> Sent: ручная сверка
    NeedsReview --> Cancelled: закрытие после сверки
    Queued --> Cancelled: отмена
~~~

1. Выдача последовательно в P0, сортировка по scheduled_utc,id, учитывать not_before, holds и режим текущего сеанса. Кнопка и таймер используют один use case. Claimed записывает lease и attempt. До intent перепроверить согласие, права, условия кампании, ссылку, фото, окна и cooldown. Последняя локальная проверка, reservation и перевод в dispatching — транзакция. CAS по state+lease защищает от опоздавшего результата. Таймер не назначает другого бота.
2. После intent вызвать Telegram вне транзакции. Подтверждение содержит chat/message ID, серверное время, fingerprint, цену из снимка. Receipt и завершение попытки — одна транзакция. Таймаут чтения, обрыв после записи, неполный ответ, неоднозначный 5xx и падение после intent → needs_review. Просроченный lease в claimed без intent можно вернуть в queued в пределах окна. На старте всегда disarmed.
3. Однозначный отказ → blocked/failed. Повтор после исправления и подтверждения. Достоверный 429 сохраняет deadline и hold в БД, приостанавливает операции аккаунта и отключает автоотправку текущего сеанса. При неизвестном deadline требуется ручная сверка. Повторы безопасных чтений ограничены и учитывают дедлайн Telegram. Записи автоматически не повторять. Для needs_review оператор фиксирует найденное сообщение или завершает запись после проверки; новое размещение требует утверждения и аудируемой связи с предыдущим. Ручная квитанция отличается от API receipt и должна совпадать с известным Chat ID; Telegram Bot API общего чтения истории не даёт, поэтому сверка выполняется в клиенте Telegram.
4. Дедуп: client key для разовой задачи, rule_id + local date/time + fold для повтора. В транзакции сравнить резервируемые слоты, последнюю отправку и неизвестные исходы по каноническому чату независимо от alias, кампании и бота. Тема не сокращает общий cooldown без явно согласованной политики. Fingerprint предупреждает о копии полезной нагрузки, повтор того же текста в согласованный новый слот допустим.
5. P0 разовые слоты. P1 еженедельные правила с конечной датой или лимитом повторов и горизонтом материализации 14 дней. Фиксировать UTC и зону ввода. DST gap пропускать с записью, fold требует выбора смещения. Запрещённое окно — paused с причиной. После сна пересчитать due; старше 1 часа требует перепланирования. Сетевые дедлайны внутри процесса используют monotonic, межзапусковые — UTC. Pause/cancel прекращает новые вызовы, после intent показывает ожидание результата.

### Analytics

P0 сохраняет ручной ввод v2, журнал попыток и базовый отчёт. Метрика хранит период, время наблюдения и источник: manual, legacy_manual, telegram_membership, telegram_financial, estimate. Истинный ноль допустим, неизвестное показывать «Нет данных». CTR и конверсию считать по одинаковому набору строк, периоду и ненулевому знаменателю. Указывать покрытие. Оценка Stars = ручные оплаты × зафиксированная цена. Отдельно показывать подтверждённый доход, если есть источник. UAH и Stars не складывать. ROI требует явно заданного курса и проверяемых исходных данных.

P1: фильтры периода, кампании, площадки, варианта, ссылки; CSV/JSON с типами, источниками, фильтрами. Накопительные снимки не суммировать, применять последнее подходящее наблюдение. Telegram-события атрибутируются при наличии точной ссылки и перехода non-member → member. Дедуп по update ID и правилам периода. «Вступление по ссылке», «повторное вступление», «продление» и «оплата» — самостоятельные метрики. Разрыв в сборе виден в отчёте. Подтверждённая оплата требует независимого финансового подтверждения.

## Дополнение от 17 ноября 2026 года

Рабочая реализация редактора использует существующие DPAPI, очередь и неизменяемый снимок. Интерфейс Publisher в executor.py принимает назначенный account ID и канонический chat ID. DesktopService выбирает BotAPITransport или UserGateway по типу сохранённого аккаунта. Исторические поля bot_account_id, таблица bot_holds и DTO telegram_bot_id сохраняют имена для совместимости старых миграций. В очереди они идентифицируют конкретного отправителя любого поддерживаемого типа. Доступ к чату проходит отдельно от решения о размещении.

Миграция 14 добавляет контактные поля аккаунта, venue_directory, venue_access, campaign_editor, версии шаблонов и флаг auto_approved. Ранее утверждённые строки получают 0 и сохраняют режим ручной отправки. Подтверждение кампании транзакционно создаёт снимок на площадку и время. Конфликт любого задания откатывает пакет. Текст, настройки подписки и ссылка остаются неизменяемыми после утверждения. Для MTProto ссылка идет в тексте, для бота доступна кнопка. У подписного предложения требуется готовая пригласительная ссылка и подтверждение реальных условий.

Qt запускает сетевые запросы в работнике. Планировщик разрешается только в текущем экземпляре приложения через явное подтверждение. Остановка блокирует следующий запрос, ставит ожидающие автоматические публикации на паузу и оставляет уже начатый запрос на обычную обработку результата. Блокировка Telegram сохраняется для выбранного отправителя. Исход после неизвестного ответа проверяется вручную. Интервал автоматического повтора отсчитывается также от фактической отправки.
